# ZSS — Zero State Snapshot

Локальный версионатор файлов для Termux и не только. Хранит историю изменений текстовых файлов, умеет откатывать, сравнивать, чистить старьё. Никакого Git, никаких серверов, никаких зависимостей кроме стандартной библиотеки Python.

## Зачем это вообще

Писалось под конкретную задачу: нужен был способ откатывать изменения в `.py` файлах прямо с телефона, без поднятия Git-репозитория. Git для этого избыточен — нужно инициализировать, коммитить, помнить про staging. ZSS делает одно: сохраняет снапшот файла при каждом изменении и даёт инструменты для работы с историей.

Работает на Android/Termux, Linux, macOS. На Windows не тестировал, но `fcntl` там не работает — сразу нет.

## Установка

Кинь `zss.py` в проект. Всё. Никаких `pip install`, никаких `requirements.txt`.

```bash
cp /path/to/zss.py ./your_project/
```

## Быстрый старт

```python
import zss

# Создаём экземпляр
tm = zss.create_timemachine(root=".zss_data")

# Сохраняем снапшоты всех .py файлов в текущей директории
tm.track()

# Смотрим историю конкретного файла
history = tm.history("main.py", limit=5)
for entry in history:
    print(f"{entry['timestamp']} | {entry['size']} bytes | hash: {entry['hash'][:8]}")

# Откатываемся к версии
tm.rollback("main.py", "2026-09-01_14-23-45_123456")

# Или по тегу
tm.add_tag("main.py", "2026-09-01_14-23-45_123456", "stable")
tm.rollback("main.py", "stable")

# Сравниваем две версии
diff_lines = tm.diff("main.py", "2026-09-01_14-00-00_000000", "2026-09-01_14-23-45_123456")
print("".join(diff_lines))

# Чистим старьё, оставляем последние 50 версий
tm.clean("main.py", keep=50)

# Удаляем данные для файлов, которых уже нет на диске
tm.purge_missing()

# Статистика
print(tm.get_stats())
```

## Архитектура

Разбил на компоненты, чтобы не было одной простыни на 800 строк. Каждый класс отвечает за своё.

### LRUCache

Кэш индексов в памяти. Хранит последние 100 индексов (настраивается). Валидация двойная: TTL + mtime файла. Если индекс изменился на диске — кэш сбрасывается. Без `OrderedDict`, использую `next(iter(dict))` для удаления старого — работает на Python 3.7+, а ниже тебе и не надо.

### FileLock

Обёртка над `fcntl.flock`. Два режима: `exclusive()` для записи, `shared()` для чтения. Лок на один файл `.lock` в корне хранилища. Не идеальное решение — на NFS не работает, на Windows тоже. Но для локальной файловой системы на телефоне — нормально.

### IndexManager

Управляет JSON-индексами. Каждый отслеживаемый файл имеет свой индекс вида `<md5_hash>.index.json`. Внутри — список версий с timestamp, hash, size, lines, path. Версия индекса = 3 (была миграция с v1).

### VersionStore

Хранит сами снапшоты. Файлы называются `<md5_hash>.<timestamp>.ztxt` (если сжатие) или `.txt` (без). Хеширование через BLAKE2b — быстрее SHA256, для версионирования достаточно. Сжатие через `zlib` — встроенный модуль, экономит 60-70% места на текстовом коде.

### TimeMachine

Координирует всё вышеперечисленное. Основной класс, с которым работаешь.

## API подробно

### `create_timemachine(root, extensions, keep_default, cache_ttl, max_cache_size, compress, block_on_secrets)`

Создаёт экземпляр. Параметры:

- `root` — куда складывать данные. По умолчанию `.timemachine`.
- `extensions` — какие файлы отслеживать. По умолчанию `[".py"]`.
- `keep_default` — сколько версий хранить при чистке. По умолчанию 100.
- `cache_ttl` — время жизни кэша индексов в секундах. По умолчанию 1.0.
- `max_cache_size` — максимум индексов в LRU. По умолчанию 100.
- `compress` — сжимать ли версии через zlib. По умолчанию True.
- `block_on_secrets` — блокировать сохранение если найдены токены/пароли. По умолчанию False.

### `track(paths=None)`

Основная функция. Сканирует файлы, сравнивает hash с последней сохранённой версией, если отличается — сохраняет новую. Возвращает dict со статистикой.

```python
result = tm.track()
# {"checked": 42, "saved": 3, "errors": 0}

result = tm.track(["main.py", "utils.py"])
# Отслеживает только указанные файлы
```

Лок берётся один раз на всю пачку файлов, а не на каждый отдельно. На 100 файлах это критично для производительности.

### `history(filename, limit=10)`

Возвращает список последних версий файла. Каждая запись — dict с `timestamp`, `hash`, `size`, `lines`, `path`, `tags`.

### `add_tag(filename, timestamp, tag)`

Привязывает имя к версии. Потом можно откатываться по имени, а не по timestamp.

```python
tm.add_tag("main.py", "2026-09-01_14-23-45_123456", "before_refactor")
tm.rollback("main.py", "before_refactor")
```

### `rollback(filename, target)`

Откат к версии. `target` — это либо timestamp, либо тег. Атомарная операция через `os.replace` — если что-то пойдёт не так, файл не останется наполовину записанным.

### `diff(filename, ts1, ts2)`

Unified diff между двумя версиями. Читает файлы построчно через генератор — не грузит всё в память. Работает с файлами любого размера.

### `clean(filename, keep=None, max_age_minutes=60)`

Удаляет старые версии, оставляя последние `keep`. Заодно чистит `.tmp` файлы старше `max_age_minutes`.

### `purge_missing(known_files=None)`

Удаляет индексы и версии для файлов, которых больше нет на диске. Если `known_files=None` — сам сканирует дерево. На больших проектах лучше передать список явно, чтобы не сканировать лишнее.

### `get_stats()`

Возвращает статистику: сколько файлов отслежено, сколько версий сохранено, сколько откатов, сколько ошибок, общий размер хранилища.

## Производительность

Тестировал на проекте с 500 `.py` файлами, суммарно 2MB кода.

- Первый `track()` — 1.2 секунды (создаёт индексы).
- Повторный `track()` без изменений — 0.3 секунды (кэш + проверка hash).
- `track()` с 10 изменёнными файлами — 0.4 секунды.

Узкое место — `fcntl.flock`. На SSD разницы не заметишь, на SD-карте в телефоне — будет медленнее.

Сжатие `zlib` добавляет ~10% к времени сохранения, но экономит место. На текстовом коде сжатие даёт 60-70%. На бинарниках — бесполезно, но они и не сохраняются.

## Ограничения

Честно скажу, что не работает или работает криво:

1. **Только текстовые файлы.** Бинарники определяются по наличию нулевого байта в первых 8KB. UTF-16 с BOM определяется, UTF-16 без BOM — нет.

2. **Нет инкрементального хранения.** Каждая версия — полная копия файла. Для больших файлов (логи > 100MB) это проблема. Delta storage не реализован — не было задачи.

3. **Нет ветвления.** Как в Git — branch, merge, cherry-pick — нет. Только линейная история.

4. **Нет сетевого режима.** Только локальная файловая система. NFS, SMB, облака — не тестировал, могут быть проблемы с локами.

5. **Однопоточность при записи.** Лок эксклюзивный — если два процесса одновременно пытаются сохранить, второй будет ждать. Для чтения локи разделяемые.

6. **Timestamp с микросекундами.** Если сохраняешь чаще 10 раз в секунду — возможны коллизии. На практике не встречал, но теоретически.

## Примеры использования

### Бэкап перед рефакторингом

```python
import zss

tm = zss.create_timemachine()
tm.track()  # Сохраняем текущее состояние
tm.add_tag("main.py", tm.history("main.py", 1)[0]["timestamp"], "before_refactor")

# ... рефакторим ...

# Если что-то сломалось
tm.rollback("main.py", "before_refactor")
```

### Отслеживание изменений в реальном времени

```python
import zss
import time

tm = zss.create_timemachine()

while True:
    result = tm.track()
    if result["saved"] > 0:
        print(f"Сохранено {result['saved']} изменений")
    time.sleep(5)
```

### Поиск когда была добавлена функция

```python
import zss

tm = zss.create_timemachine()
history = tm.history("main.py", limit=100)

for entry in history:
    # Читаем версию и ищем строку
    content = tm._store.get_version_bytes(
        __import__("pathlib").Path("main.py").resolve(),
        entry["timestamp"]
    )
    if b"def new_feature" in content:
        print(f"Функция появилась в версии {entry['timestamp']}")
        break
```

### Очистка старого хлама

```python
import zss
from pathlib import Path

tm = zss.create_timemachine()

# Чистим все .py файлы, оставляем по 20 версий
for py_file in Path(".").rglob("*.py"):
    tm.clean(str(py_file), keep=20)

# Удаляем данные для удалённых файлов
tm.purge_missing()

print(tm.get_stats())
```

## Known issues

1. **KeyboardInterrupt внутри лока.** Если нажмёшь Ctrl+C во время `track()`, лок освободится корректно (контекстный менеджер), но может остаться `.tmp` файл. Чистится автоматически при следующем `clean()`.

2. **Символические ссылки.** Игнорируются. Если файл — symlink, он не сохраняется. Сделано намеренно, чтобы не ходить по круговым ссылкам.

3. **Права доступа.** Если нет прав на чтение файла — пропускается с warning в лог. Если нет прав на запись в хранилище — будет исключение.

4. **Повреждённые индексы.** Если JSON-индекс битый (ручное редактирование, сбой диска) — создаётся новый с нуля. Старые версии файлов остаются, но теряется связь с ними.

## FAQ

**Почему не Git?**
Git требует инициализации, staging, коммитов. Для быстрого снапшота "сохранить перед изменением" это overkill. ZSS делает одно действие — `track()`.

**Почему не использовать файловую систему (cp file file.bak)?**
Неудобно искать нужную версию, нет истории, нет diff, нет автоматической очистки. ZSS структурирует хранение.

**Можно ли использовать с другими языками?**
Да. Параметр `extensions` настраивается. Можно отслеживать `.js`, `.ts`, `.go`, `.rs`, что угодно текстовое.

**Что если файл удалён?**
ZSS не заметит. Индекс и версии останутся. Чтобы почистить — вызови `purge_missing()`.

**Что если два процесса работают одновременно?**
Лок синхронизирует запись. Второй процесс будет ждать. Чтение параллельное.

**Можно ли зашифровать версии?**
Нет. Если нужна шифровка — делай на уровне файловой системы (fscrypt, ecryptfs). В ZSS это не заложено.

**Почему BLAKE2b, а не SHA256?**
BLAKE2b быстрее в 3-5 раз на больших файлах. Для версионирования коллизии не критичны — если hash совпал, файл не изменился. Вероятность коллизии на 8 байтах — 1 на 2^64, этого достаточно.
