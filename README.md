ZSS — шифрованный Python-рантайм в одном файле

Меня зовут prime41k автор этого проекта, и я хочу рассказать вам, что такое ZSS, зачем я его сделал, как он работает и — что не менее важно — где он не работает и не должен применяться. Я специально написал README так, чтобы вы понимали границы инструмента и не строили на нём защиту, которую он не может дать. Это не реклама и не инструкция по обходу — это честный разговор о том, для чего инструмент годится, а для чего нет.



С чего всё началось

Я пишу на Python много лет. И каждый раз, когда нужно поделиться скриптом с кем-то, кто не должен видеть часть кода, я упираюсь в одну и ту же стену. Отдать открытый .py — значит отдать всё: алгоритмы, ключи, лицензионные проверки, служебные константы. Скомпилировать в .pyc — бессмысленно, дизассемблируется за минуту. Обфусцировать — только замедляет чтение, но не останавливает. Упаковать в бинарник через PyInstaller — теряется переносимость, растёт размер, и всё равно распаковывается.

Мне хотелось простого: чтобы часть кода на диске лежала в зашифрованном виде, а в момент запуска расшифровывалась на машине с правильным ключом. Без бинарной сборки, без внешних сервисов, без сложной инфраструктуры. Один файл, который можно скопировать на любую машину с Python и библиотекой cryptography, и он работает.

Так появился ZSS — Zero State Snapshot. Название отражает идею: код существует в двух состояниях — зашифрованном «снимке» на диске и живом исполняемом состоянии в памяти, и переход между ними происходит только по вашему ключу.



Как это выглядит в работе

Работа делится на три шага, и я постарался сделать каждый максимально простым.

Первый шаг — инициализация. Вы один раз запускаете:


zss init


Программа создаёт пару ключей X25519. Приватный ключ ложится в ~/.zss/keys/master.x25519 с правами 0600 — читать его можете только вы. Публичный ключ сохраняется рядом. Ещё создаётся зашифрованный файл состояния ~/.zss/zss.zson, где хранятся настройки и служебные данные. Этот шаг делается один раз на машине.

Второй шаг — разметка. В своём .py вы оборачиваете фрагменты, которые хотите спрятать, двумя служебными комментариями:


#<zss>{write_to!секрет.zspy
API_KEY = "abc123"

def проверка_лицензии():
    ...
#<zss>{closing!write!секрет.zspy


Имя внутри директивы — это имя будущего .zspy-файла. Оно должно быть простым идентификатором с расширением .zspy, без путей и без ... Это сделано специально: директива не должна уметь писать в произвольное место файловой системы.

Третий шаг — упаковка:


zss pack мой_скрипт.py

Программа находит все размеченные блоки, шифрует каждый в отдельный .zspy-файл рядом с исходником, сохраняет резервную копию исходника с расширением .bak и пишет новый .py-файл, где каждый блок заменён на короткую заглушку from zss import load; load("секрет.zspy").

Запускается уже этот новый файл. Заглушка при исполнении расшифрует свой .zspy и выполнит код прямо в пространстве имён вызывающего модуля — так, будто он всегда там был. С точки зрения остальной программы ничего не изменилось: все переменные и функции, определённые в спрятанном блоке, доступны так же, как если бы были прописаны прямо в файле.



Что под капотом

Я не изобретал криптографию. Все примитивы — стандартные, проверенные, используемые в серьёзных продуктах.

X25519 — обмен ключами на эллиптической кривой. Лежит в основе Signal, WireGuard, TLS 1.3. Быстрый, компактный, хорошо изученный.

HKDF-SHA256 — вывод ключей из общего секрета. Стандартный механизм, чтобы из одного материала получить несколько независимых ключей для разных целей.

ChaCha20-Poly1305 — аутентифицированное шифрование. Один алгоритм и шифрует, и проверяет целостность. Если хоть один байт шифртекста изменён, расшифровка провалится с ошибкой, а не вернёт мусор.

Схема состоит из двух уровней.

Первый уровень — обёртка мастер-ключа. У каждого .zspy-файла есть собственный случайный мастер-ключ на тридцать два байта. Этот ключ упакован на публичный ключ получателя. Для каждой упаковки генерируется новая эфемерная пара ключей, из общего секрета выводится симметричный ключ, им шифруется мастер. Расшифровать может только владелец приватного ключа — он делает обратный обмен и получает тот же общий секрет.

Второй уровень — многослойное шифрование кода. Мастер-ключ через HKDF порождает N производных ключей. Исходный код шифруется последовательно N раз. Расшифровка идёт в обратном порядке, с проверкой тега на каждом слое. По умолчанию N равно пяти, максимум двести пятьдесят пять.

Скажу честно про эти N слоёв, потому что вокруг этого легко обмануться. Криптостойкость определяется одним слоем — ChaCha20-Poly1305 уже обеспечивает надёжную защиту. Остальные слои не делают шифр крепче. Они нужны как обфускация и как паранойя на случай, если однажды один из слоёв будет скомпрометирован. Не рассчитывайте, что N=40 даст вам «в сорок раз больше защиты» — это не так.

Каждый слой шифруется с привязкой к контексту через AAD — дополнительные данные, которые не шифруются, но участвуют в вычислении тега. В AAD подмешивается соль файла, номер слоя и общее количество слоёв. Это защищает от пересадки: если попытаться склеить шифртексты из разных файлов или переставить слои местами, тег не сойдётся.

Дополнительно в заголовок пишется SHA-256 от исходного кода. После расшифровки хеш сверяется. Технически AEAD-теги уже гарантируют целостность, но эта проверка — ещё один слой паранойи.

Отдельный файл ~/.zss/zss.zson хранит настройки и кеш. Он тоже зашифрован. Ключ для него выводится детерминированно из вашего приватного ключа. Соль лежит в открытом виде в заголовке файла — это не секрет, это просто параметр для вывода ключа. Секретен только приватный ключ.



Парсер директив — почему это не регулярка

На первый взгляд поиск директив в файле — задача на одну регулярку. Но директива может случайно оказаться внутри строкового литерала. Или в многострочной строке. Или в f-строке. Или в docstring. Наивный построчный парсер на таком сломается и либо найдёт ложную директиву, либо пропустит настоящую.

Поэтому я использую стандартный токенизатор Python — tokenize. Он разбирает исходник на токены и точно знает, что является комментарием, а что строкой. Парсер берёт только токены типа COMMENT и ищет директивы только среди них. Всё, что внутри строк, игнорируется.

Дальше парсер ведёт стек открытых блоков. Открывающая директива кладёт блок в стек, закрывающая снимает. Проверяется совпадение имён, запрещается вложенность, ловятся незакрытые блоки и закрытия без открытия. Все ошибки ведут к понятному сообщению с номером строки.

Имена файлов валидируются строгой регуляркой, которая запрещает пути, .., абсолютные адреса, начинающиеся с цифры. Это не случайность: .zspy создаётся рядом с исходником, и директива не должна иметь возможности писать в произвольное место.

Для замены блока на заглушку парсер вычисляет точные позиции в символах, вырезает всё между директивами, вставляет заглушку с сохранением отступа. Результат — новый исходник, в котором видны только заглушки.



Загрузка в рантайме

Когда упакованный .py исполняется, он встречает from zss import load; load("секрет.zspy"). Функция load находит в стеке вызовов кадр вызывающего модуля, берёт оттуда его __file__, чтобы понять, в какой директории искать .zspy. Это позволяет одной и той же упакованной программе работать из любого места: .zspy всегда рядом с .py.

Дальше файл читается, парсится заголовок, грузится приватный ключ, идёт расшифровка строго по порядку. Сначала распаковка мастер-ключа с проверкой тега обёртки. Потом расшифровка слоёв в обратном порядке с проверкой тега каждого слоя. Потом сверка хеша. Если хоть один шаг провалился — исключение, никакого частичного плейнтекста наружу не выходит.

Расшифрованный код компилируется и исполняется через exec в глобалах вызывающего модуля. Это тонкий момент: код выполняется так, будто он написан прямо в этом месте, а не в отдельной функции. Все имена из .zspy становятся доступны снаружи — как если бы вы объявили их прямо в .py. Это и есть задуманная семантика инлайна, но она требует аккуратности от того, кто размечает код.

Есть ловушка, которую я обошёл в zss run. Когда пользователь пишет zss run файл.py, а внутри файла написано from zss import load, Python попытается импортировать модуль zss с диска — то есть загрузит второй экземпляр со своими глобальными переменными и своим ZSS_HOME. Это привело бы к тому, что настройки, применённые в командной строке, не подхватились бы в рантайме. Поэтому на время исполнения код подменяет sys.modules["zss"] на текущий запущенный модуль. Импорт возвращает именно его.



Где ZSS помогает, а где нет

Теперь самое важное, и я хочу сказать это прямо, без обиняков. Понимание границ инструмента — это не путь к его обходу, это условие его правильного применения. Если вы будете использовать ZSS там, где он не может работать, вы получите ложное чувство защищённости, и это хуже, чем не использовать его вовсе.

ZSS помогает, когда код в покое лежит на диске, в репозитории, в архиве, в бэкапе, в пересылке. Когда кто-то скопировал ваш проект и хочет прочитать содержимое .zspy — он увидит только шифртекст. Когда вы отдаёте демо-сборку и не хотите раздавать часть логики — она будет зашифрована. Когда у вас внутренняя утилита и вы не хотите, чтобы фрагменты с ключами или константами разошлись по команде — они зашифрованы.

ZSS не помогает, когда атакующий имеет контроль над машиной, на которой код исполняется. Это принципиальное ограничение, а не недостаток реализации. В момент запуска код расшифровывается в памяти процесса — и если этот процесс кому-то доступен через отладчик, через дамп памяти, через инструментирование интерпретатора, через чтение памяти другого процесса с соответствующими правами, — расшифрованный код будет прочитан. Шифрование на диске здесь ничем не поможет. Я не буду перечислять конкретные способы, потому что не хочу превращать README в инструкцию, но принцип именно такой: расшифрованный код живёт в памяти, и в этой точке его можно перехватить.

ZSS не помогает против копирования приватного ключа. Ключ лежит файлом в ~/.zss/keys/. Он защищён правами доступа, но это защита от других пользователей на той же машине, а не от того, кто получил доступ к вашей учётной записи. Если ключ скопирован на другую машину — .zspy расшифруются и там. Привязки к железу в ZSS нет и не планируется: это другая задача и другие инструменты.

ZSS не заменяет лицензионную защиту, DRM, продажу кода как продукта с контролем копий. Для этого нужны серверные проверки, привязка к оборудованию, обфускация уровня коммерческих протекторов. ZSS — не про это.

ZSS не даёт гарантий затирания секретов в памяти. Python принципиально не предоставляет надёжного способа стереть байты. Функция zero_fill в коде зануляет bytearray, но это лишь копия. Оригинальные байты в неизменяемых bytes остаются в куче до сборки мусора, скомпилированный объект code остаётся в памяти, строки неизменяемы. Настоящего secure-erase в Python нет. Я делаю что могу, но не обещаю невозможного.

ZSS находится в бете. В открытом исходнике видны начальные байты _SEED_PEPPER и _SEED_SALT, которые используются только при первом запуске для бутстрапа файла состояния. После первого init они зануляются в памяти, но в исходнике на диске остаются. Это осознанный компромисс открытой беты. В бинарной сборке их не будет. Пока исходник открыт — считайте, что эти конкретные байты публичны.

Я подчёркиваю все эти ограничения не для того, чтобы дать кому-то план атаки, а чтобы вы трезво оценивали, что покупаете. ZSS — это защита в глубину для данных в покое. В этой роли он работает. За пределами этой роли — не работает, и я не хочу, чтобы у кого-то создалось впечатление обратного.



Почему я выбрал именно такую схему

Можно было сделать проще — шифровать весь файл целиком симметричным ключом. Но тогда ключ пришлось бы распространять отдельно, и вся безопасность сводилась бы к тому, как вы его передаёте. Асимметричная схема позволяет отдавать публичный ключ кому угодно: им можно только шифровать, расшифровать нельзя. Упаковать .zspy может любой, у кого есть публичный ключ. Прочитать — только владелец приватного.

Можно было использовать готовый ECIES из библиотеки. Но я собрал схему из явных примитивов, чтобы каждый шаг был виден и понятен — что из чего выводится, что чем шифруется, что где проверяется. Меньше магии, больше прозрачности.

Можно было обойтись без многослойности. Но N слоёв дают дешёвую обфускацию и запас прочности на будущее. При этом я специально не делаю вид, что это сильно повышает стойкость.

Можно было парсить директивы регуляркой. Но тогда директива внутри строкового литерала сломала бы всё. tokenize — правильное решение, хоть и более сложное.

Можно было писать .zson в JSON. Но JSON на диске виден, а я не хотел светить даже настройки и кеш. Поэтому .zson — бинарный зашифрованный контейнер.



Команды


zss init                        создать ключи и файл состояния
zss init --force                перезаписать существующие ключи
zss init --profile имя          задать имя профиля

zss pack файл.py                упаковать все блоки в .zspy
zss pack файл.py --layers N     задать число слоёв
zss pack файл.py --in-place     перезаписать исходник вместо .packed.py
zss pack файл.py --no-clobber   не перезаписывать существующий .bak

zss run файл.py                 запустить упакованный .py
zss run файл.zspy               запустить .zspy напрямую
zss run файл.py -- аргументы    передать аргументы скрипту

zss list                        посмотреть, что где упаковано
zss list --json                 то же в машиночитаемом виде
zss list --dir путь             сканировать другую директорию

zss test                        запустить встроенные тесты
zss test -v                     подробнее


Переменная окружения ZSS_HOME переопределяет директорию ~/.zss. Это удобно для тестов, для нескольких профилей, для изоляции.



Тесты

В файл встроен набор тестов на unittest, около пятидесяти штук. Они покрывают парсер, криптографию, оба формата, утилиты и полный цикл упаковки-запуска. Фикстура _ZssHomeFixture подменяет ZSS_HOME на временную директорию, чтобы тесты не трогали реальный ~/.zss. Запускаются командой zss test или python zss.py test.

Тесты — это не формальность. Я писал их параллельно с кодом, и они не раз ловили ошибки в граничных случаях парсера и в согласовании форматов. Если вы будете что-то менять — прогоняйте их.



Что я хочу, чтобы вы вынесли из этого README

ZSS — это аккуратно сделанный инструмент для одной конкретной задачи: держать часть Python-кода зашифрованной на диске и расшифровывать её в момент запуска на машине с правильным ключом. В этой роли он работает хорошо. Криптография стандартная, форматы продуманы, парсер грамотный, тесты подробные.

Он не заменяет защиту от серьёзного атакующего с доступом к работающему процессу. Он не привязывает код к железу. Он не обеспечивает DRM. Он не даёт гарантий затирания памяти. Всё это я написал явно, чтобы у вас не было иллюзий.

Если вы потеряли ключ — расшифровать .zspy уже не получится, никак. Это не баг, это свойство. Резервную копию ключа делайте сами, я за вас этого не сделаю. Если ключ утёк — считайте, что утёк и код. Если процесс скомпрометирован — считайте, что код прочитан. ZSS защищает данные на диске, в покое, при передаче. За пределами этого — не защищает, и я не буду делать вид, что защищает.

Используйте его там, где он уместен. Тогда он вас не подведёт.
